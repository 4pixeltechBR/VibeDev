## 🇺🇸 English

**Release date:** 2026-07-24
**Scope:** VibeDev v1.7.0 + VibeShield v2.0.0
**Type:** Minor (VibeDev) + Major (VibeShield — scope change, no behavior break)

This release closes the structural improvements from the Onda B plan. VibeDev gets Changesets workflow. VibeShield gets a dedicated `code-review` skill and `.out-of-scope/` documentation.

### What's in this release

#### 1. Changesets workflow at repo root

VibeDev now uses [Changesets](https://github.com/changesets/changesets) for version management, inspired by mattpocock/skills.

- `.changeset/config.json` — Changesets config tied to `4pixeltechBR/VibeDev` repo
- `.changeset/README.md` — how to add a changeset during a PR
- `.changeset/initial-setup.md` — first changeset (this release itself)

**How it works (current state, human-driven):**
1. Each PR that changes behavior adds a `.changeset/<name>.md` describing the change
2. At release time, the maintainer (or future bot) runs `pnpm changeset version`
3. Changesets become CHANGELOG entries + commit + tag
4. The maintainer creates the GitHub Release

**Why not full automation now?** The bot integration is a separate concern. The tooling is in place. When the maintainer decides to wire a bot (probably v3.7.0 or later), it's a small config change, not a new architecture.

#### 2. VibeShield v2.0.0 — scope change

VibeShield was at v1.0.0 since launch. Bumping to v2.0.0 reflects:

- **New skill dedicated** to code review
- **New `.out-of-scope/`** documentation following the same pattern as VibeDev
- **No behavior change** to existing G1-G7 audit triggers, C1-C8 categories, or envelope format

The major version bump is **honest about scope change** without breaking anything existing.

#### 3. `vibeshield-code-review` — dedicated skill

New file `vibeshield/commands/code-review.md`. User-invoked (human types the command).

**Differentiates from audit gatilho (G1-G7):**

| Audit (G1-G7) | Code-review |
|---|---|
| Triggers on risky sub-tasks automatically | Triggered by human calling `/vibeshield-code-review` |
| Focus on C1-C8 security categories | Focus on 2 axes: **Standards** + **Spec** |
| Output: OK/REVISAR/BLOQUEAR | Output: list of findings + verdict |
| Auto when sub-task touches auth/data/API/deploy | Manual when human wants a full diff review |

**2 axes reviewed:**

- **Standards** — does the code follow project conventions? Naming, structure, error handling, logging, tests, dependencies.
- **Spec** — does the code do what the active sub-task's "pronto" criterion said? Cases covered? Anti-scope respected? Type 1 decisions followed?

Inspired by [`code-review` from mattpocock/skills](https://github.com/mattpocock/skills) (cited as competitive reference), but adapted to VibeDev's context: the review is done **against the project state** (`PROJECT_STATE.md`), not just a raw diff.

#### 4. VibeShield `.out-of-scope/`

6 documents explaining what VibeShield does NOT do:

- `not-a-pentest.md` — we audit code, not deployed systems
- `not-replacing-dpo-lawyer.md` — we flag, we don't provide legal advice
- `not-a-sast-tool.md` — we don't replace Semgrep/Snyk/CodeQL
- `not-covering-runtime-race-conditions.md` — static analysis, not runtime
- `not-audit-transitive-deps.md` — we audit the project, not the full dep tree
- `not-replacing-vibedev.md` — we're a satellite, not a project manager

Same pattern as VibeDev's `.out-of-scope/`. Same audience, different skill.

### Backward compatibility

- **VibeDev** (v1.6.0 → v1.7.0): pure addition (Changesets tooling). No behavior change.
- **VibeShield** (v1.0.0 → v2.0.0): new skill dedicated + new docs. Existing G1-G7 audit, C1-C8 categories, envelope format: all unchanged.
- **Handoff contract** (vibedev ↔ vibeshield): preserved. v3.6.0 ↔ v2.0.0.

### Why VibeShield goes 2.0.0 and not 1.1.0

Semantic Versioning says: "MAJOR version when you make incompatible API changes". This release doesn't break any existing functionality. But it does add a **new skill dedicated** (not just a reference), a new directory, and bumps scope meaningfully.

Honest call: v1.1.0 would be a lie about the size of the change. v2.0.0 is the right call because the ecosystem sees a real new surface (`/vibeshield-code-review` command). The behavior of existing triggers stays the same — but that's a separate axis from "scope expanded".

Inspirado em [`code-review` de mattpocock/skills](https://github.com/mattpocock/skills) (citado como referência competitiva), mas adaptado pro contexto VibeDev: revisão é feita **contra o estado do projeto** (`PROJECT_STATE.md`), não só contra diff cru.
