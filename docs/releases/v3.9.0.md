# Release v3.9.0 — Motor de Fundação Técnica (`/vd-scaffold`)

🌍 **Read in / Leia em:** [English](#-english) | [Português](#-português)

## 🇺🇸 English

**Release date:** 2026-07-26
**Scope:** VibeDev v2.0.0 (major — first since v1.0.0)
**Type:** Major — significant new capability.
**VibeShield version:** unchanged (v2.0.0)
**Inspired by:** Dante Testa — Prompt Mestre WordPress v1.14.0 (jul/2026)

This release adds the **foundation engine** to VibeDev. Where `/vd-build` was
generic (one sub-task at a time, no protocol for foundation), `/vd-scaffold`
brings structured, idempotent, BR-first foundation generation for the **Phase 3
— Architecture** of the Green Trail.

### What's in this release

#### 1. `/vd-scaffold` sub-command

`vibedev/commands/vd-scaffold.md`. Activated automatically as a gate in
`/vd-build` when ALL of:
- Trail = Green
- Current phase = **Phase 3 — Architecture**
- Sub-task involves any of: data modeling, auth/permissions, payments,
  multi-tenancy, white-label, initial folder structure

Cynefin-lite triage (max 3 questions) + Red Team + 4 real components generated
(schema, RBAC, payment, white-label). Idempotent. Stack-agnostic.

#### 2. Six reference docs

Each component is documented in its own reference file:

- **`scaffold-stack-validada.md`** — 3 pre-validated stacks by Cynefin profile
  (Complicated: FastAPI+React+TS+Postgres · Simple: Next.js+SQLite · Edge: legacy
  coexistence as Type 1 high uncertainty).
- **`scaffold-schema-migrations.md`** — schema-agnostic with 6 mandatory rules
  (id UUID, created/updated, soft delete, indexes, FK with ondelete, multi-tenancy).
  Examples in Alembic (Python) and Drizzle (TS).
- **`scaffold-rbac.md`** — 4D matrix (Role × Resource × Action × Scope) +
  3 implementation options (column, table, Casbin/Oso). Always generates the
  domain-specific version, never delivers a template.
- **`scaffold-pagamento-br.md`** — **BR-first** payment (PIX + Mercado Pago
  + Asaas as primary, Stripe as fallback). **Idempotent webhook mandatory**
  (UNIQUE on `(provider, event_id)`). Reconciliation job for PIX pending >1h.
  LGPD Art. 46 + PCI-DSS 4.0 compliance.
- **`scaffold-white-label.md`** — tokens per tenant (colors, fonts, logo,
  favicon, domain, support email). 3 options (CSS vars, Tailwind, Emotion).
  **Hardcode forbidden** (gate H2 suggested for `/vd-check`).
- **`scaffold-legado-coexistencia.md`** — edge case Cynefin (WordPress, ERP,
  spreadsheet). Always Type 1 high uncertainty. 3 options: keep legacy,
  migrate everything, bidirectional sync (Strangler Fig + CDC).

#### 3. Devil's Advocate gate integration (v3.8 + v3.9)

If `Stack decidida` in `PROJECT_STATE.md` is **already filled** but the
Cynefin triage suggests a different stack, `/vd-devils-advocate` is triggered
(v3.8 gate) with the tension as the internal contradiction. Stack tension
becomes conscious decision, not automatic override.

#### 4. `stack_trocada` metric

New metric in `PROJECT_STATE.md` → `## Métricas do framework`. Increments
when the stack chosen in Triage is reverted later. Self-evaluation signal:
if it goes up, **review the 3 Triage questions before reviewing the code**.

### Why "sub-command" and not "4th skill"?

Three reasons:

1. **Trigger is phase-specific** (only Phase 3 of Green Trail), not standalone
2. **Cost is lower** — sub-command is cheap, skill is heavy
3. **Maintains "family of 3 skills"** (VibeDev, VibeShield, vd-arch-review)
   — keeps the ecosystem cohesive

The pattern is the same as `/vd-devils-advocate` (v3.8) and `/vd-manual` (v3.8):
sub-commands of VibeDev, not new skills.

### Backward compatibility

- `/vd-scaffold` only fires if Trail=Green + Phase=3 + sub-task involves
  foundation. In any other context, it's a no-op.
- Opt-out via `--skip-scaffold` flag.
- Three skill families unchanged. `/vd-scaffold` is sub-command of VibeDev, not 4th skill.
- Fully compatible with v3.8 (Devil's Advocate) — integrates, doesn't replace.

### What's next

- **v4.0 (major):** Gate H2 of VibeShield (design tokens heuristic) implemented.
- **v4.0 (major):** `vd-status` v2 with visual map including scaffold.
- **v4.x:** Scaffold for Node.js (Express + TS + Postgres) and Go (Gin + Postgres).
- **v4.x:** Automatic ER diagram from schema.

#### 3. Integração com Advogado do Diabo (v3.8 + v3.9)

Se `Stack decidida` em `PROJECT_STATE.md` está **preenchida** mas a triagem
Cynefin sugere outra stack, `/vd-devils-advocate` é disparado (gate v3.8) com
a tensão como contradição interna. Tensão de stack vira decisão consciente,
não override automático.

#### 4. Métrica `stack_trocada`

Nova métrica em `PROJECT_STATE.md` → `## Métricas do framework`. Incrementa
quando a stack escolhida na Triagem é revertida depois. Sinal de auto-
avaliação: se subir, **revisar as 3 perguntas da Triagem antes de revisar o código**.

### Por que "sub-comando" e não "4ª skill"?

Três razões:

1. **Trigger é fase-específico** (só Fase 3 da Trilha Verde), não standalone
2. **Custo é menor** — sub-comando é barato, skill é pesado
3. **Mantém "família de 3 skills"** (VibeDev, VibeShield, vd-arch-review) —
   ecossistema coeso

O pattern é o mesmo do `/vd-devils-advocate` (v3.8) e `/vd-manual` (v3.8):
sub-comandos de VibeDev, não skills novas.

### Compatibilidade

- `/vd-scaffold` só roda se Trilha=Verde + Fase=3 + sub-tarefa envolve
  fundação. Em qualquer outro contexto, é no-op.
- Opt-out via flag `--skip-scaffold`.
- 3 famílias de skills inalteradas. `/vd-scaffold` é sub-comando de VibeDev, não 4ª skill.
- Compatível com v3.8 (Advogado do Diabo) — integra, não substitui.
